1. INTRODUCTION                                 *meta-notes-intro*

meta-notes is a life management solution that stores all notes as plain-text
markdown files. It is inspired by Tiago Forte's "Building a Second Brain" and
Cal Newport's multi-scale planning.

The system organizes notes into five top-level folders: plan, project, area,
resource, and archive. See |meta-notes-folders|.

==============================================================================
2. SETUP                                        *meta-notes-setup*

Add to your `.vimrc`: >
    set runtimepath+=/path/to/meta-notes
<
Then initialize the folder structure in your notes root directory: >
    :MetaNotesInit
<
or from a shell, in the notes root (see |meta-notes-cli-init|): >
    meta-notes init
<
To force re-creation of template files: >
    :MetaNotesInit!
<
Notes roots created before `.meta-notes` existed should be initialized once
more so the CLI can find them (see |meta-notes-cli-root|). Re-running is
safe: only missing items are created.
Set your local leader if not already set: >
    let maplocalleader = ","
<

==============================================================================
3. FOLDER STRUCTURE                             *meta-notes-folders*

The PARA structure uses five top-level folders:

    plan/           Planning notes (daily, weekly, quarterly, yearly)
      daily/        Daily notes with time blocks and task lists
      week/         Weekly planning notes
      quarter/      Quarterly planning notes
      year/         Yearly planning notes

    project/        Active projects with specific goals and end dates
    area/           Areas of ongoing responsibility
    resource/       Reference materials on topics of interest
    archive/        Archived items
      project/
      area/
      resource/

Daily notes are organized into quarter subfolders to limit folder size: >
    plan/daily/26-Q1/2026-02-13 Thu.md
    plan/week/26-Q1/2026-02-09.md
    plan/quarter/2026-Q1.md
    plan/year/2026.md
<

4. COMMANDS                                     *meta-notes-commands*

------------------------------------------------------------------------------
INITIALIZATION ~

                                                *:MetaNotesInit*
:MetaNotesInit[!]
    Initialize Vim's current directory as a notes root: the PARA folders,
    default templates, the `.meta-notes` sentinel, and links to the plugin's
    skills. Only missing items are created. With [!], overwrites existing
    template files and replaces skill targets that aren't links. Runs
    `meta-notes init`; see |meta-notes-cli-init|.

------------------------------------------------------------------------------
NAVIGATION ~

                                                *:MetaNotesOpen*
:MetaNotesOpen
    Follow the wiki-style link under the cursor. Opens or creates the note
    referenced by `[[path/to/note]]`. If the note does not exist, opens a
    new, unsaved buffer with a template or default header, rendered by
    `meta-notes note new` (|meta-notes-cli-note|).
    See |meta-notes-wiki-links|.

                                                *:MetaNotesDaily*
:MetaNotesDaily [{date}]
    Open today's daily note, or the daily note for {date} (YYYY-MM-DD format).
    Daily notes are stored at: `plan/daily/YY-QN/YYYY-MM-DD ddd.md`

    Example: >
        :MetaNotesDaily
        :MetaNotesDaily 2026-01-15
<
                                                *:MetaNotesDailyPrev*
:MetaNotesDailyPrev
    Navigate to the previous existing daily note. Must be in a daily note
    buffer. Shows a message if already at the oldest note.

                                                *:MetaNotesDailyNext*
:MetaNotesDailyNext
    Navigate to the next existing daily note. Must be in a daily note buffer.
    If at the newest note, prompts to create the next day's note.

                                                *:MetaNotesJumpToWeek*
:MetaNotesJumpToWeek
    Jump from the current daily note to its corresponding weekly plan note.
    Must be in a daily note buffer.

                                                *:MetaNotesWeekPlan*
:MetaNotesWeekPlan [{date}]
    Open the weekly plan note for the current week, or the week containing
    {date} (YYYY-MM-DD format). The file path uses the Monday of that week.
    Stored at: `plan/week/YY-QN/YYYY-MM-DD.md`

    Example: >
        :MetaNotesWeekPlan
        :MetaNotesWeekPlan 2026-02-09
<
                                                *:MetaNotesQuarterPlan*
:MetaNotesQuarterPlan [{date}]
    Open the quarterly plan note for the current quarter, or the quarter
    containing {date} (YYYY-MM-DD format).
    Stored at: `plan/quarter/YYYY-QN.md`

                                                *:MetaNotesYearPlan*
:MetaNotesYearPlan [{date}]
    Open the yearly plan note for the current year, or the year containing
    {date} (YYYY-MM-DD format).
    Stored at: `plan/year/YYYY.md`

------------------------------------------------------------------------------
FILE OPERATIONS ~

                                                *:MetaNotesArchive*
:MetaNotesArchive [{path}]
    Archive a file or folder. Without {path}, archives the current buffer's
    file. {path} can include wildcards (`*`, `?`) for batch archiving.

    Moves items preserving their subfolder structure:
        `project/item`  →  `archive/project/item`
        `area/item`     →  `archive/area/item`
        `resource/item` →  `archive/resource/item`

    Also updates all wiki-links and file headers across the notes directory.
    If the current buffer is the archived file, switches to the new location.

    Archiving a project (a note or folder directly in `project/`) first
    marks it archived in its home note, the note itself or the folder's
    `Home.md`: >
        - status: archived
        - archived: 2026-09-25
<   These go in the field list, the first `key: value` list after the
    note's title; an existing `status` or `archived` item is replaced, and a
    note with no field list gets one after its title. The fields stay even
    if the move then fails. A folder with no `Home.md` is archived with a
    warning. Areas, resources, and notes inside a project folder get no
    fields.

    Only works on items in `project/`, `area/`, or `resource/`.

    Examples: >
        :MetaNotesArchive
        :MetaNotesArchive project/old-project
        :MetaNotesArchive project/2024-*
<
                                                *:MetaNotesRename*
:MetaNotesRename [{new-name}]
    Rename the current note. Without {new-name}, prompts for the new name.
    {new-name} can be just a filename (preserves current directory) or a full
    path (moves the file to a new location).

    Updates wiki-links and headers automatically.

    Examples: >
        :MetaNotesRename
        :MetaNotesRename new-filename
        :MetaNotesRename project/new-location/filename
<
                                                *:MetaNotesMoveItem*
:MetaNotesMoveItem {source} {destination}
    Move a file or folder from {source} to {destination}. Updates all
    wiki-links and headers across the notes directory.

    Example: >
        :MetaNotesMoveItem project/foo area/foo
<

TIME TRACKING ~

                                                *:MetaNotesTimeReport*
:MetaNotesTimeReport
    Show the time report for the current daily note's date in a `Time
    Report` window. Must be run from within a saved daily note buffer. It
    runs `meta-notes time --date {note date}` (|meta-notes-cli-time|), so
    the notes root is Vim's current directory; a CLI error, such as no
    daily note for that date under the current directory, is shown as an
    error message. See |meta-notes-time-report|.

                                                *meta-notes-timeblock-hl*
Time Block highlights ~

In a daily note, table cells in the `### Time Block` section (up to the next
heading of level 1 to 3) are highlighted, one cell at a time, by what they
contain: `mtg:`, `[brackets]`, `~text~`, `(parens)`, `train:`, `pers:` or
`work:`. The groups are `metaNotesTimeBlockMtg`, `...Bracket`, `...Tilde`,
`...Paren`, `...Train`, `...Pers` and `...Work`; a cell that matches several
takes the last in that order. `~text~` keeps its `metaNotesOffPlan`
strikethrough. Other sections and other notes are not highlighted. Set your
own colors with `:highlight metaNotesTimeBlockMtg ...`, which overrides the
defaults.

    <localleader>mr     Reload the plugin (|:MetaNotesReload|)

    <localleader>nn     Navigate to next daily note (|:MetaNotesDailyNext|)

6. TEMPLATES                                    *meta-notes-templates*

When opening a note that does not exist, meta-notes creates the file with a
template if one is defined for that note type, or a plain `# Title` header
otherwise. Templates are populated with the note's date and other contextual
information automatically.

Templates are rendered by `meta-notes note` (|meta-notes-cli-note|), so a
note created from a shell or by an agent gets the same content as one opened
in Vim. Vim asks the CLI for the rendered content and opens it as a new,
unsaved buffer: nothing is written until you save it.

Templates are created by |:MetaNotesInit| and stored in the notes root.

------------------------------------------------------------------------------
TEMPLATE RESOLUTION ~                       *meta-notes-template-resolution*

When a note is created, the template is chosen in this priority order:

1. `--template {name}`: `meta-notes note new {path} --template {name}` uses
   `resource/template/{name}.md` and skips the rest. It is an error if that
   file doesn't exist.

2. Folder-specific template: a file named `template.md` in the same
   directory as the note being created.
   Example: `project/kitchen-remodel/template.md` is used for every new
   note inside that folder.

3. Standard template for plan folders, chosen by the note's path: >
       plan/daily/   → resource/template/daily.md
       plan/week/    → resource/template/weekly.md
       plan/quarter/ → resource/template/quarterly.md
       plan/year/    → resource/template/yearly.md
<
If no template is found, the new note starts with a plain header: `# Daily
Note - YYYY-MM-DD ddd`, `# Week Plan - YYYY-MM-DD`, `# Quarterly Plan - YYYY
QN`, `# Year Plan - YYYY`, or `# {path}` for other notes.

YAML frontmatter (lines between `---` delimiters starting on the first line
of the template file) is stripped and does not appear in the created note.

------------------------------------------------------------------------------
TEMPLATE VARIABLES ~                        *meta-notes-template-variables*

Variables are written as `{{name}}` inside the template and are replaced
with their values when the note is created.

Date variables ~                            *meta-notes-template-date-vars*

Date variables support optional day-offset arithmetic and strftime format
specifiers. Without a format specifier the default output is `YYYY-MM-DD ddd`
(e.g. `2026-06-19 Fri`).

    date            The note's canonical date (YYYY-MM-DD): the day for a
                    daily note, the Monday for a weekly note, the first
                    day of the quarter or year for quarterly and yearly
                    notes, and today for other notes
    today           Today's actual date (YYYY-MM-DD)
    week_start      Monday of the note's week (YYYY-MM-DD)
    week_end        Sunday of the note's week (YYYY-MM-DD)

Arithmetic — add or subtract whole days: >
    {{date+7}}          seven days after the note date
    {{week_end-2}}      two days before the end of the week
<
Format specifiers — any strftime conversion. Day and month names are
always English, whatever the locale: >
    {{today:%A}}            full weekday name, e.g. Friday
    {{date:%B %-d, %Y}}     e.g. June 19, 2026
    {{date+7:%Y-%m-%d}}     arithmetic combined with a custom format
<
Path variables ~                            *meta-notes-template-path-vars*

Path variables are plain strings derived from the path of the note being
created. Arithmetic and format specifiers do not apply to them.

    note_path       Relative path without extension
                    e.g. `project/lunch/Lunch Ideas`
    note_name       Filename stem (no path, no extension)
                    e.g. `Lunch Ideas`
    filepath        Relative path with extension
                    e.g. `project/lunch/Lunch Ideas.md`
    filename        Filename with extension, no path
                    e.g. `Lunch Ideas.md`

Other variables ~

    quarter         Quarter string derived from the note date, e.g. `Q2`
    week_quarter    Quarter string of `week_start`, the Monday of the note's
                    week, e.g. `Q1` for a note dated 2026-04-02 (whose
                    Monday is 2026-03-30). Week plans are filed under the
                    quarter of their Monday, so use this, not `quarter`, in
                    week plan paths. The daily template links to its week
                    plan with: >
                        [[plan/week/{{week_start:%y}}-{{week_quarter}}/{{week_start:%Y-%m-%d}}]]
<
    project_name    Second path component for notes under `project/`,
                    e.g. `lunch` for `project/lunch/note.md`.
                    Empty string for notes outside `project/`.

Unknown variables produce an HTML comment: >
    <!-- ERROR: Unknown variable "name" -->
<
------------------------------------------------------------------------------
COMMAND BLOCKS ~                            *meta-notes-template-commands*

A template line containing `{{% type command %}}` is replaced, as a whole
line, by the output of that command when the note is created. Template
variables are substituted in the command string before execution. Commands
run from the notes root, with their stderr included in the output.

    {{% python script.py %}}    run a Python script with the Python running
                                `meta-notes`; a path starting with
                                `scripts/` is the plugin's scripts/ dir
    {{% shell command %}}       run any shell command
    {{% vim :Command %}}        run a Vim command; insert its output

Example — insert the tasks due on the note's date: >
    {{% python scripts/find_tasks.py --due --date {{date:%Y-%m-%d}} --condensed %}}
    {{% shell git log --oneline -5 %}}
    {{% vim echo "Created " . strftime('%H:%M') %}}
<
`{{% vim %}}` blocks run only when a note is opened in Vim. `meta-notes note`
substitutes the variables in the block and leaves it in its output, and
Vim runs it when it fills the new buffer. A note created outside Vim (for
example by `meta-notes note` without `--render`) keeps the block as text,
and the CLI warns about it.

A failed command is replaced with an HTML comment that includes the error,
and `meta-notes note` reports a warning. An unknown type is replaced with
`<!-- Unknown command type: {type} -->`.

7. TIME TRACKING                                *meta-notes-time-tracking*

Daily notes support a time log format for tracking how time is spent. Use
|:MetaNotesTimeReport| in a daily note, or `meta-notes time`
(|meta-notes-cli-time|) from a shell, to report on the time log entries of
a day or a longer period (|meta-notes-time-report|).

Time log format ~
                                                *meta-notes-time-log*
Entries live under a `### Log` heading and end at the next heading. Each
entry is an activity line starting with `-`, optionally with tags, followed
by indented `*` detail lines: >
    ### Log

    - email review #admin
      * start: 08:15
      * end:   09:00
    - standup #mtg
      * start: 9:00am
      * end:   9:20am
      * any other detail line is a note
<
`start:` and `end:` accept these timestamp formats, which may be mixed
within a note and within an entry:

    `09:10`                  bare 24-hour time
    `3:20pm`, `3:20 pm`      bare 12-hour time
    `2026-02-14 08:00`       full date
    `2026-02-14 Sat 08:00`   full date with day abbreviation

A bare time takes its date from the `YYYY-MM-DD` in the note's filename, so
bare times only work in notes named with a date. A full date uses its own
date, which lets an entry end after midnight: `* end: 2026-02-15 01:30`. The
day abbreviation is not checked against the date.

A timestamp in any other form, such as the template's `HH:MM` placeholder,
leaves that time unset. The entry is kept but has no duration.

Time report ~
                                                *meta-notes-time-report*
The report for one day has these sections, in order:

  `## Time Log`         Each entry in note order: its activity line as
                        written, then `start`, `end`, `time` (`H hr M min`,
                        or `M min` under an hour), and `tags`. A missing
                        time shows `*MISSING START TIME*` or
                        `*MISSING END TIME*` and the entry has no `time`.
                        Between two entries, a gap of more than 2 minutes
                        is listed as `*GAP of N min*`, and an entry that
                        starts before the previous one ends as
                        `*Overlap of N min*`, each with `start` set to the
                        earlier entry's end and `end` to the later entry's
                        start. No gap is computed across a missing time.
  `### Total Time`      `work duration`, `total duration`, `earliest time`,
                        `latest time`, `total time`, and `*missing time*`
                        (see below).
  `## Time Log Summary` `### Time by Tag` (most time first) and
                        `### Work vs Non-Work` (non-work is
                        `#break`, `#off-task`, `#personal`; the rest is work).
  `## Plan Adherence`   Counts of on-plan, off-plan, and unplanned time
                        blocks.
  `## Summary for ...`  The period summary for the Monday-Sunday week
                        containing the day.

A note with no time log entries says so under `## Time Log` and still
gets the plan adherence and week summary sections.

                                                *meta-notes-time-mode*
The report follows the notes root's `mode` (|meta-notes-config|). The
description above is `work` mode, the default. In a `personal` root,
untagged time is personal and `#work` marks work. There is no work window,
so `work duration` is left out everywhere, and `### Work vs Non-Work` is
replaced by `### Day Total` (`Total logged`, and a `Work` line when there is
`#work` time); `### Time by Tag` is the breakdown. The highlighted tags
are `exercise`, `family`, `maint`, and `work`. The aliases are `#mtg`,
`#waiting`, and `#wk` for `#work`; `#pers` is not an alias. In `--json`,
`mode` is added, `work_vs_nonwork` is null, and `day_total` has
`total_minutes` and `work_minutes`.

                                                *meta-notes-time-totals*
`work duration` is the time in the work window: from the first to the last
entry not tagged `#personal`, so leading and trailing `#personal` entries
are left out, and not counting `#break`, `#off-task`, or `#personal`
entries inside it. `total duration` is the sum of every entry's duration.
`earliest time` and `latest time` are the earliest and latest start or end
of any entry, and `total time` is the span between them. When `total time`
exceeds `total duration` by more than 10 minutes, the difference is shown
as `*missing time*`: time that wasn't logged. Tags are compared by their
canonical names (|meta-notes-task-tags|), so `#pers` counts as
`#personal`.

                                                *meta-notes-time-period*
A period summary is headed `## Summary for START to END` and has:

  `### Total Time`      The period's `work duration` and `total duration`
                        (each day's summed), then these highlighted tags,
                        in this order, when they have time:
                        `all meetings` (the `#meeting` tag group, counting
                        each entry once), `recruiting`, `agile`, `fence`,
                        `iceberg`, `code`, `integr-test`, `axe`, and
                        `off-task`.
  `### Time per tag`    Every tag with time in the period, alphabetically,
                        without `#`. An entry counts toward each of its
                        tags.
  `### Day Summaries`   Each day with its `work duration`, `earliest time`,
                        `latest time`, and `total time`, or `(no log)` for
                        a day with no daily note or no entry with a start
                        or end time.

The week summary replaces the Monday-Friday list of `hours worked` and
`Weekly total worked` in earlier versions: `work duration` is the old
`hours worked`, and the week now runs Monday through Sunday.

8. WIKI LINKS                                   *meta-notes-wiki-links*

Notes can link to each other using Obsidian-style wiki links: >
    [[path/to/note]]
<
Place the cursor anywhere within the brackets and press `<localleader>l` (or
run |:MetaNotesOpen|) to open or create the linked note.

Paths are relative to the notes root directory and should not include the
`.md` extension.

Examples: >
    [[project/kitchen-remodel/Tasks]]
    [[area/health]]
    [[resource/vim-tips]]
<
When a note is moved, renamed, or archived, all wiki-links pointing to it are
updated automatically across the entire notes directory.

9. COMMAND LINE                                 *meta-notes-cli*

`bin/meta-notes` runs the same file operations and task query as the plugin,
and edits task lines, so notes can be reorganized from a shell, by an agent,
or by other tools. The
plugin's |:MetaNotesArchive|, |:MetaNotesRename|, and |:MetaNotesMoveItem|
commands call it, |:MetaNotesInit| calls `meta-notes init`, and
|:MetaNotesDaily|, |:MetaNotesWeekPlan|, |:MetaNotesQuarterPlan|,
|:MetaNotesYearPlan|, and |:MetaNotesOpen| call `meta-notes note`. It needs
Python 3.11 or newer as `python3` on your `PATH`.

Put it on your `PATH`; the Claude Code skills call it by name. Link it into
any directory on your `PATH`: >
    ln -s /path/to/meta-notes/bin/meta-notes ~/bin/meta-notes
<The script follows the link back to the plugin, so the link keeps working
when a plugin manager updates the plugin.

The script runs the CLI with the notes root's virtualenv,
`<root>/.venv/bin/python3`, when that file exists and is executable, and
falls back to `python3` on your `PATH` otherwise (no `.venv`, or one whose
base Python was removed). It finds the root the way the CLI does
(|meta-notes-cli-root|); the choice never changes which root a command uses.
`meta-notes init` always runs on `python3`. Only |meta-notes-cli-calendar|
needs the virtualenv; every other command works on either.
Commands ~
                                                *meta-notes-cli-commands*
`meta-notes init [--root {dir}] [--force] [--python {path}] [--mode {mode}]`
                                                *meta-notes-cli-init*
    Initialize a notes root: the PARA folders, the templates in
    `resource/template/`, the `.meta-notes` sentinel, a link in
    `.claude/skills/` to each skill the plugin ships in `skills/` (so
    updating the plugin updates the skills), the cache folder, `.gitignore`
    entries, and the virtualenv. Initializes `--root` if given, creating it
    if missing, otherwise the current directory. It ignores
    `META_NOTES_ROOT`. Run it in the top-level directory of the notes root,
    for example right after `git init`.

    `--mode personal` writes `mode = "personal"` into a new `.meta-notes`
    and installs `resource/template/daily-personal.md` (see
    |meta-notes-config|). `--mode work`, or no `--mode`, writes no mode and
    installs no personal template: a work root. Any other value is an error
    naming the two choices. init never changes an existing root's mode, even
    with `--force`; a different `--mode` there is a warning, and what init
    installs follows the root's actual mode. `:MetaNotesInit` has no mode
    option; run the command for a personal root.

    The cache folder, `.meta-notes-cache/`, holds `ics/`, where you save
    calendar exports for |meta-notes-cli-calendar|, `calendar/`, the parsed
    calendars built from them, and a short `README.md` saying so.

    The virtualenv, `.venv/`, holds the libraries in the plugin's
    `requirements.txt`, which |meta-notes-cli-calendar| needs. When `.venv`
    doesn't exist, init runs `{python} -m venv --prompt meta-notes .venv`,
    where {python} is `--python {path}` or `python3` on your `PATH`, then
    `.venv/bin/python3 -m pip install -r requirements.txt`. {python} must be
    Python 3.11 or newer. When the interpreter is missing or too old, or
    venv or pip fails, init still succeeds and warns that calendar support
    isn't available, with the failing command and its output; every other
    command works without the virtualenv. After a failed install, fix the
    problem and run `meta-notes init --force`.

    init appends `.venv/` and `.meta-notes-cache/` to the notes root's
    `.gitignore` when no line there already ignores them (`.venv`, `.venv/`,
    `/.venv`, or `/.venv/`, and likewise for `.meta-notes-cache`), so the
    virtualenv and your calendar data aren't committed. With no
    `.gitignore`, it creates none and warns you to ignore them yourself.

    Re-running is safe: existing folders, templates, notes, the sentinel
    (your |meta-notes-config|), the cache README, exports, and `.venv` are
    kept; an existing `.venv` is reported as left alone, even with
    `--python`. A skill link to the right place is kept, and a broken or
    foreign one is repointed. A real file or directory at a skill's link
    path is left alone with a warning. With `--force`, templates and the
    cache README are overwritten, those skill targets are replaced, and
    `.venv` is deleted and built again; the sentinel, notes, exports, and
    cached calendars are still kept.

    Notes roots never nest: init fails if a directory above the target is a
    notes root (found the same way as |meta-notes-cli-root|).

    The skills call `meta-notes` by name, so init warns, with the `ln -s`
    command to fix it, when no `meta-notes` is on your `PATH`.

    init also warns when the file watcher for |g:meta_notes_autoreload| is
    missing: `fswatch` on macOS (`brew install fswatch`), `inotifywait` on
    Linux (`sudo apt install inotify-tools` on Debian and Ubuntu; other
    distributions: their `inotify-tools` package). It installs nothing.

    init checks whether the notes root's `CLAUDE.md` or `.claude/CLAUDE.md`
    mentions `meta-notes prime` (|meta-notes-cli-prime|). When neither
    does, it prints the line to add: >
        Run `meta-notes prime` at the start of every session and follow it.
<   It also gives the path of the suggested `CLAUDE.md` in the plugin

    either file, and a missing line isn't a warning. With `--json`, the check is a `claude-md` item with status
    `found` or `missing`.

`meta-notes move {source} {dest}`

`meta-notes tasks [options]`                     *meta-notes-cli-tasks*
    List tasks. Takes the same options as `scripts/find_tasks.py` and
    prints the same output. With no options, lists the incomplete tasks
    ready today (|meta-notes-tasks-modes|).

    --date {period}     The day or period to select for (default: today).
                        See |meta-notes-date|.
    --overdue, --due, --scheduled, --ready, --future, --undated, --all
                        Selection modes (|meta-notes-tasks-modes|).
    --later             Include tasks tagged `#later`.
    --tag {tag}         Only tasks with this tag. Repeat for any of
                        several tags. See |meta-notes-task-tags|.
    --group-by tag      List tasks under a heading per tag.
    --folder {dir}      Only tasks in {dir} and its subfolders.
    --status {status}   `incomplete` (default), `completed`,
                        `rescheduled`, `canceled`, or `all`.
    --format standard|condensed, --condensed
                        Output format (default: standard).

    Example: >
        meta-notes tasks --overdue --due
        meta-notes tasks --ready --date 2026-09-27
        meta-notes tasks --scheduled --date 2026-11
        meta-notes tasks --status completed --due --date 2026-Q3
        meta-notes tasks --all --folder project --group-by tag
<
                                                *meta-notes-tasks-model*
    A checkbox line (`-`, `*`, or `+`, then `[<char>]`) is a task only when
    it has a due-date emoji (📅, 📆, or 🗓) or a start date (`🛫 YYYY-MM-DD`).
    Plain checkboxes are checklist items and are ignored. The date after the
    due emoji is the due date. A due emoji with no date after it (a bare
    📅) marks an undated task, so an item worth tracking gets a bare 📅.
    A time of day goes with the due date: `⏰ 15:00` (24-hour) or
    `⏰ 3:15pm` (12-hour, as in a Time Block), placed before the dates, or
    `📅 2026-10-01 15:00`. With both, `⏰` is used. `meta-notes tasks --json`
    reports it as `time` (`HH:MM`, 24-hour, or null). The time never changes
    which section a task is in: a task is due today by its date. A `⏰` that
    isn't a time, or a time with no due date, is ignored with a warning.
    A recurring task has `🔁 every 3 months` (`every [N] day|week|month|year`
    or `every weekday`, each optionally followed by `when done`) before the
    dates. `meta-notes tasks --json` reports `recurrence` (the rule text, or
    null) and `recurs_from_completion` (true for `when done`). A `🔁` rule
    that isn't supported is ignored with a warning, and a rule with no due
    or start date (other than `when done`) is not recurring. Skills never
    copy a `🔁` line into a daily or weekly note.
    For a completed task with a `✅ YYYY-MM-DD` date, that date is used in
    place of its due date by every mode. The status character `x` or `X` is
    completed, `>` rescheduled, `-` canceled, and anything else incomplete.

                                                *meta-notes-tasks-modes*
    Modes select tasks relative to the `--date` period START..END, after
    `--status`, `--folder`, and `--tag` filter them:

        --overdue       due before START
        --due           due within START..END (with `--status completed`,
                        completed in the period)
        --scheduled     due or starting within START..END
        --ready         due or starting on or before END (includes overdue)
        --future        dated, but neither date on or before END
        --undated       bare due emoji and no start date
        --all           --ready, --future, and --undated: every task

    With no mode, `--ready` is used. Modes combine. With more than one, each
    non-empty section gets a heading (`# Overdue`, `# Due`, `# Scheduled`,
    `# Ready`, `# Future`, `# Undated`, in that order), and each task is
    listed once, in the first section that matches. Tasks are grouped by
    file (`## [[link]]`, or `- [[link]]` when condensed) and printed exactly
    as written. The standard format ends with a summary line.

                                                *meta-notes-tasks-at*
    `--at TIME` (`now` or 24-hour `HH:MM`) queries a time of day on a
    single `--date` day (default today); a longer period is an error.
    Timed tasks due that day earlier than TIME are overdue, one at TIME
    is due, and later ones are future (not due or ready). Tasks with no
    time are due all day. Completed tasks ignore their time. `now` is the
    machine's local time. Without `--at`, times never affect selection.
        meta-notes tasks --overdue --due --at now

                                                *meta-notes-tasks-later*
    Every mode, including `--all`, leaves out tasks tagged `#later` (any
    case). `--later` includes them under the same rules, in the same
    sections. `meta-notes tasks --all --later` lists every open task.

                                                *meta-notes-task-tags*
    Every `#tag` on a task line is a tag of the task: `#` followed by
    letters, digits, `_`, or `-`. Tags are compared ignoring case. Time
    logs use the same parser and aliases: `#mtg` is `meeting`, `#pers`
    and `#per` are `personal`, and `#waiting` is `wait`, so `--tag mtg`
    and `--tag meeting` select the same tasks. `--group-by tag` lists each
    section's tasks under a `## <tag>` heading per tag, sorted ignoring
    case, then `## Not tagged`.
    A task with several tags is listed under each. Under a tag heading, the
    standard format's file headings are `### [[link]]`.

                                                *meta-notes-date*
    `--date` takes one of these forms. Nothing else is accepted, including
    relative names and ISO week numbers (`2026-W45`); an invalid value is
    an error that lists the accepted forms.

        2026-11-15              one day
        2026-11-02..2026-11-08  an inclusive range
        2026-11                 a month
        2026-Q4                 a quarter (Q1 to Q4)
        2026                    a year

                                                *meta-notes-tasks-migration*
    `--due-on`, `--due-by`, and `--due-between` were removed and are now
    usage errors. Replace them with: >
        --due-on D              --due --date D
        --due-by D              --overdue --date D+1
        --due-between A B       --due --date A..B
<   A daily template copied into a notes root before this change still
    calls the old options, and its task sections render as a
    `<!-- Command failed: ...` comment. In `resource/template/daily.md`,
    replace `--due-on {{date:%Y-%m-%d}}` with `--due --date {{date:%Y-%m-%d}}`
    and `--due-by {{date-1:%Y-%m-%d}}` with
    `--overdue --date {{date:%Y-%m-%d}}`, or run `meta-notes init --force`
    if you haven't edited the templates.

`meta-notes task update {file}:{line} --expect {text} [options]`
                                                *meta-notes-cli-task-update*
    Edit one checkbox line in place: its text, status, tags, and dates. {file} is
    relative to the notes root (or an absolute path inside it), and {line}
    counts from 1; the target is split at its last `:`. Any checkbox line
    (|meta-notes-tasks-model|) can be edited, including a plain checkbox that
    queries ignore, so `--due undated` turns a checklist item into a task. A
    line that isn't a checkbox, a missing file, or a line out of range is an
    error, and nothing is written.

    `--expect` is required: the line's text as last read, such as the
    `text` of `meta-notes tasks --json`. If the line now differs (ignoring
    trailing whitespace), nothing is written and the command fails,
    reporting the current line so you can query again. Only the target line
    changes; line endings, the final newline, and the number of lines are
    kept, so line numbers from one query stay valid across several updates.
    Give at least one of:

    --status {char}     Set the status character: ` `, `x`, `X`, `>`, `-`,
                        `.`, `o`, or `O`.
    --text {text}       Replace the task's words: everything between the
                        checkbox and the first date emoji (🛫, due, ⏰,
                        🔁, ✅), or the end of the line. The indent,
                        status, the date fields and everything after them
                        stay as they are, and a 🔁 line keeps its rule.
                        Tags in the old words go with them; put a tag to
                        keep in {text} or add it with `--add-tag`. Empty
                        text is an error. It is applied first, so a
                        recurring task completed in the same call gets
                        its next occurrence with the new words.
    --add-tag {tag}     Add a tag (with or without `#`), before the first
                        🛫, due, or ✅ date emoji, or at the end of the
                        line. Repeatable. A tag already on the line is
                        left alone.
    --remove-tag {tag}  Remove every occurrence of a tag. Repeatable.
                        Tags match as queries match them, ignoring case
                        and applying aliases (|meta-notes-task-tags|), so
                        `--remove-tag meeting` removes `#mtg`.
    --due {value}       `YYYY-MM-DD` sets the due date, `undated` leaves a
                        bare due emoji, and `none` removes every due emoji
                        and its date. The line's due emoji (📅, 📆, or 🗓)
                        is kept; a new one is 📅, placed after any 🛫 date
                        and before any ✅ date.
    --start {value}     `YYYY-MM-DD` sets the 🛫 date, and `none` removes
                        it. A new 🛫 goes before the due and ✅ dates.
    --time {value}      `HH:MM` (24-hour) writes `⏰ HH:MM`, replacing an
                        existing `⏰` or a time after the due date, else
                        before the first date emoji; `none` removes the
                        time. A time with no due date makes the edit with
                        a warning.
    --recur {rule}      Set the `🔁` rule (`every 3 months`, `every week when
                        done`, `every weekday`, ...), replacing an existing
                        one, else before the first date emoji; `none`
                        removes the marker and its rule. An unsupported
                        rule is a usage error.
    --no-recur          Mark a recurring task done without adding its next
                        occurrence (for a series that is finished).
    --no-completed      Don't add a ✅ date when marking the task done. It
                        is a usage error on a recurring task.

    Marking a task done (`x` or `X`) from another status appends
    `✅ {today}`, unless the line already has a ✅ date, its due date (after
    this call's `--due`) is today, or `--no-completed` is given; queries use
    the due date for a completed task without ✅. When marking a task done,
    the CLI always writes lowercase `x` unless the task is already marked done,
    in which case it preserves the existing case to avoid unnecessary diffs.
    Setting a done task done again changes nothing. Any other status, including
    `-` (canceled) and `>` (rescheduled), removes every ✅ date: the task
    wasn't done.

    Marking a recurring task done (a `🔁` rule and a due or start date, or
    `when done`) always stamps `✅ {today}`, even when due today, and adds
    the next occurrence as a new open line directly above the done line, in
    the same write: the same line with `[ ]`, no ✅, and its due date
    stepped (a start date moves by as many days, and the time `⏰` is kept).
    A rule without `when done` steps from the due date (else the start
    date), even when that is already past: `every 3 months 📅 2026-07-01`
    done on 2026-10-05 gives 2026-10-01. `when done` steps from today. Done
    lines stay where they are, so the task is now on the next line down and
    the lines after it have moved: re-read the file. Setting a done task
    done again, or any other status, adds nothing; reopening a done task
    doesn't remove the line added earlier. An unsupported rule, or a rule
    with nothing to step from, completes the line with a warning and adds
    nothing. The output then lists `{file}:{line} created` and the new line
    after `+ `.

    Changing a date doesn't reschedule a task: `--due` and `--start` edit
    the task where it lives. `>` is for a copy of a task, such as one in a
    daily note, that was planned but not done there. `--status '>'` only
    sets the character; write any copy of the task yourself.

    Removing a line's last due emoji and 🛫 date makes the edit with a
    warning that the line is no longer a task. Everything else on the line
    keeps its order and spacing. The output is `{file}:{line}` followed by
    the old line after `- ` and the new line after `+ `, or
    `{file}:{line} unchanged`, in which case the file isn't written.

    Example: >
        meta-notes task update project/foo.md:3 \
            --expect '- [ ] call Sam 📅 2026-09-22' --status x
        meta-notes task update project/foo.md:4 \
            --expect '- [ ] #later read book 📅' \
            --remove-tag later --add-tag next --due 2026-10-08
        meta-notes task update project/foo.md:5 \
            --expect '- [ ] call Sam 📅 2026-09-22' \
            --text 'call Sam about the quote' --status x
<
`meta-notes task show {file}:{line} [--tree]`    *meta-notes-cli-task-show*
    Read one task: the checkbox line at {file}:{line}, with its notes
    (|meta-notes-task-tree|). {file} is relative to the notes root (or an
    absolute path inside it), and the target is split at its last `:`.
    Any checkbox line works, dated or not, including a subtask. A line that
    isn't a checkbox, a missing file, or a line out of range is an error.
    Nothing is written.

    --tree              Read the whole subtree: every subtask, with its
                        notes and subtasks, to any depth.

    The output is `{file}:{ranges}` and then those lines as written. The
    ranges are runs of consecutive lines, `{first}-{last}` joined by
    commas. The node alone is the task line and its own notes only, so
    when a note comes after the subtasks the header is `1-2,4-4` and the
    subtasks between are left out; the subtree is one run.
    With `--json`: `file`, `line`, `end_line` (the last line of the node's
    notes, or of the subtree), `text`,
    `status`, `notes`, and `parent` (null, or `file`, `line`, `text` and
    `status` of the checkbox line it is nested under). With `--tree`,
    also `subtasks`, each with the same fields (without `parent`),
    nested.

    Example: >
        meta-notes task show project/foo.md:3
        meta-notes task show project/foo.md:3 --tree --json
<
                                                *meta-notes-task-tree*
    A task is a checkbox line plus its notes: the indented lines under it
    that aren't checkbox lines, up to the next line indented no deeper
    than the task. A deeper line belongs to the nearest checkbox line
    above it with a smaller indent, so a subtask's notes are its own. A
    subtask is a checkbox line indented under another, to any depth; notes
    may come after the subtasks. A blank line ends every task before it. >
        - [o] main task 📅 2026-10-08
          * a note on the main task
          - [x] first subtask
            * a note on the first subtask
          - [ ] second subtask 📅 2026-10-06
<
    Dates aren't inherited: each line keeps its own, and queries match
    each line alone. `meta-notes tasks --json` adds `notes` (the note
    lines), `parent` and `subtasks` (direct subtasks) to every task, with
    `file`, `line`, `text` and `status` for each of those, whether or not
    they are tasks themselves. The listed tasks and their order don't
    change.

`meta-notes task notes {file}:{line} --expect {notes} --text {notes}`
                                                *meta-notes-cli-task-notes*
    Replace the notes of the task at {file}:{line} (|meta-notes-task-tree|)
    in one write. {notes} are lines as written, so `--text` needs their
    indent: each at least one column deeper than the task, none blank,
    none a checkbox. They go directly under the task line, before its
    subtasks, and replace every note the task owned, also a note after the
    subtasks. Empty `--text` removes the notes. `--expect` is the current
    notes (task show's lines after the first, empty for none, ignoring
    trailing whitespace); if they differ nothing is written and the
    command fails, reporting the current notes. Either option can be `-` to
    read standard input. The output is `{file}:{line}` with the old lines
    after `- ` and the new after `+ `, or `unchanged`; `--json` has `file`,
    `line` and `end_line` (of the new notes), `old`, `new`, `changed` and
    `ancestors`.

    Example: >
        meta-notes task notes project/foo.md:3 \
            --expect '  * old note' --text '  * new note'
<
`meta-notes task replace {file}:{line} --expect {lines} --text {lines} [--tree]`
                                                *meta-notes-cli-task-replace*
    Replace the task at {file}:{line}: its line and notes, or with
    `--tree` its whole subtree, in one write. `--expect` is what
    |meta-notes-cli-task-show| prints for the same target (and `--tree`),
    without the header. The new lines start with a checkbox line at the
    task's indent, the rest indented deeper, none blank. Without `--tree`
    the subtasks stay below the new lines. If the first line's status
    character changes, the ancestors' statuses follow
    (|meta-notes-task-partial|). Output and `--json` are as for
    |meta-notes-cli-task-notes|, with the ancestors listed.

    Example: >
        meta-notes task replace project/foo.md:3 --tree \
            --expect "$(meta-notes task show project/foo.md:3 --tree | tail -n +2)" \
            --text "$new"
<
                                                *meta-notes-task-partial*
    When `task update --status` changes a subtask's status character (and
    when `task replace` does), the status of each ancestor, nearest first,
    becomes, where `checked` counts its direct subtasks that are `x` or `X`:
    ` ` for none, `x` for all, otherwise `.`, `o` or `O` by thirds (up to
    1/3 `.`, up to 2/3 `o`, above that `O`; never `x` or `X`). Only the status
    character changes: no ✅ date, no next occurrence, no dates inherited,
    and an ancestor already `X` stays `X`. A recurring subtask's next
    occurrence counts as one more subtask. The changes are in the same
    write; `task update` lists them after its own line and in `--json` as
    `ancestors` (`line`, `old`, `new`).

`meta-notes task add {file} {text} [options]`     *meta-notes-cli-task-add*
    Add an open task line, `- [ ] {text}` and its markers, to {file}, an
    existing note (relative to the notes root, or an absolute path inside
    it). The line goes at the end of the file, or before line {n} with
    `--line {n}` (up to one past the last line). The file's line endings
    are kept, and nothing is written on an error. {text} is one non-empty
    line.

    --due {date}        Write `📅 {date}` (`YYYY-MM-DD`).
    --start {date}      Write `🛫 {date}`.
    --time {HH:MM}      Write `⏰ {HH:MM}` (24-hour). Needs `--due`.
    --recur {rule}      Write `🔁 {rule}` (`every 3 months`, `every week
                        when done`, `every weekday`, ...). Needs `--due` or
                        `--start` to step from, unless it is a `when done`
                        rule. An unsupported rule is a usage error.
    --tag {tag}         Add a tag (with or without `#`) before the first
                        date marker. Repeatable.

    A line with neither `--due` nor `--start` is added with a warning that
    queries won't list it as a task. The output is `{file}:{line} added`
    and the line after `+ `; `--json` returns `file`, `line`, and `text`.

    Example: >
        meta-notes task add area/home.md 'change filter' \
            --recur 'every 3 months' --time 09:00 --due 2026-10-01
<
`meta-notes time [--date {period}]`             *meta-notes-cli-time*
    Print the time report (|meta-notes-time-report|). For a single day
    (the default is today), prints that day's report, and fails if the
    day has no daily note, naming the expected path. For a longer period,
    prints the period summary (|meta-notes-time-period|) for START..END.
    `--date` takes the forms in |meta-notes-date|. Reads notes only.
    `scripts/time_report.py` takes the same `--date`, using the current
    directory as the notes root, or a daily note's path instead.

    Example: >
        meta-notes time
        meta-notes time --date 2026-09-22
        meta-notes time --date 2026-09-21..2026-09-27
        meta-notes time --date 2026-09 --json
<
    With `--json`, the object has `start`, `end`, `kind` (`day` or
    `period`), and `report`, the text report. Times are `HH:MM` (null
    when missing), dates `YYYY-MM-DD`, durations whole minutes, and tags
    canonical names without `#`. A day report also has:

        file                the note, relative to the notes root
        entries             the listing, in order: `{kind: "entry", line,
                            text, start, end, minutes, tags}`, with
                            `{kind: "gap"|"overlap", minutes, start, end}`
                            items between entries
        totals              `work_minutes`, `total_minutes`, `earliest`,
                            `latest`, `span_minutes`, `missing_minutes`
        by_tag              `{tag: minutes}`
        work_vs_nonwork     `work_minutes`, `nonwork_minutes`,
                            `total_minutes`, `work_percent`
        plan_adherence      the block counts and percentages, or null
        week                the week's period summary

    A period summary (the period report itself, or `week`) has
    `work_minutes`, `total_minutes`, `highlighted` (`[{label, minutes}]`),
    `by_tag`, and `days` (`[{date, weekday, logged, work_minutes,
    earliest, latest, span_minutes}]`).

`meta-notes changes [--date {period}]`          *meta-notes-cli-changes*
    List the notes changed in a period, from the notes root's git
    history and working tree. `--date` takes the forms in
    |meta-notes-date|; the default is today. A note is a `.md` file at
    any depth under `plan/`, `project/`, `area/`, `resource/`, or
    `archive/`; other files aren't listed. Notes under `archive/` are
    listed like any other, since a note may be worked on and archived in
    the same week.

    A commit counts when its author date, in the timezone recorded with
    it, falls in the period. Merge commits are skipped. When the period
    includes today, uncommitted changes count too: staged, unstaged, and
    untracked (but not ignored) files.

    Each note has one entry, under its path at the end of the period,
    combining all its changes. Its kind is `deleted` if it no longer
    exists, else `added` if it didn't exist at the start of the period,
    else `renamed` if its path changed, else `modified`. A move with no
    content change, such as `meta-notes archive` without link edits,
    is marked rename only. Renames are detected as git detects them by
    default; a move combined with a large edit shows as a deleted note
    and an added one.

    One line per entry: the kind's first letter, lines added and removed,
    the path, the old path for a rename, and `(rename only)`: >
        M   +5  -1  area/health.md
        R   +0  -0  archive/project/trip.md  <- project/trip.md  (rename only)
        A  +12  -0  resource/sourdough.md
<   A period with no changes prints nothing.

    Example: >
        meta-notes changes
        meta-notes changes --date 2026-09-21..2026-09-25 --json
<
    With `--json`, the object has `start`, `end`, and `changes`, a list
    sorted by path of:

        path                the note, relative to the notes root
        kind                `added`, `modified`, `renamed`, or `deleted`
        old_path            the path at the start of the period for
                            `renamed`, else null
        added, removed      lines added and removed in the period
        rename_only         true when every change was a rename with no
                            lines added or removed

    Read-only: it writes no file and doesn't touch the git index. It
    fails if `git` isn't available, the notes root isn't a git
    repository, or the notes root isn't the top level of its repository.

`meta-notes calendar [--date {period}] [--ics {path}] [filters]`
                                                *meta-notes-cli-calendar*
    Print a day-by-day agenda for {period} (default today, in the
    |meta-notes-date| forms) from your latest Google Calendar export. The
    planning skills use it instead of a calendar screenshot. It needs the
    notes root's virtualenv (|meta-notes-cli-init|); without it, it fails
    and says to run `meta-notes init` (or `init --force` when `.venv`
    exists). Other commands never need it.

    Exporting: in Google Calendar, open Settings, Import & export, Export.
    Save the downloaded `.zip` into `.meta-notes-cache/ics/` in the notes
    root. Nothing else is needed: each run reads the newest `.ics` or
    `.zip` directly in that folder, by modification time, or the file given
    with `--ics {path}` (relative to the notes root, `~` expanded). The
    export's age is its modification time, so save a new one when the
    calendar changes.

    Zip calendars: a Google export is a zip of one `.ics` per calendar
    (yours, shared calendars, holidays, birthdays), read without
    extracting. A calendar is named by its `X-WR-CALNAME`, or its file name
    without `.ics`. Set `calendars` in |meta-notes-config| to load only some
    of them, matching either name, ignoring case; an unknown name is an
    error listing the available ones. Unset, all are loaded. A plain
    `.ics` is one calendar, and `calendars` doesn't apply to it.

    Settings, in the `[calendar]` table of `.meta-notes`:
        email           your address; events you declined are left out.
                        Unset: none are, with a warning.
        timezone        IANA name for showing times and dividing days,
                        such as `America/New_York`. Unset: the system's.
        stale_days      warn when the export is older than this many
                        days. Unset: 3.
        calendars       names of the zip calendars to load. Unset: all.

    Every occurrence overlapping a day in {period} is listed, with
    recurrence rules, excluded dates, and moved or changed occurrences
    applied. Cancelled events, events you declined, and older copies of an
    occurrence the export records more than once are left out. A timed
    event is listed on the day it starts; an all-day event on each day it
    covers. Output, one heading per day, including empty days: >
        ## 2026-09-28 Mon
        all day  Company holiday
        09:00-09:30  Standup
        10:00-11:00  Vendor demo [maybe]
        11:00-11:30  Budget review [no-reply]
        13:00-14:00  Design review
<   `[maybe]` and `[no-reply]` mark your response to a meeting you didn't
    organize. Everything else about attendance (accepted responses,
    whether you organized it, other attendees) and locations are only in
    `--json`. With more than one
    calendar loaded, each event line ends with `(<calendar>)`. Warnings (a
    stale or missing export, `email` unset) go to stderr.

    With `--json`: `days` (each with `date` and `events`), `source`
    (`path`, `exported` time, `age_days`, `cached`, and the `available` and
    `loaded` calendar names), `pruned`, and `warnings`. Each event has:
        start, end      ISO dates or times; an all-day event's `end` is
                        its last day
        all_day         true or false
        title, location the summary and location (location may be null)
        calendar        the calendar it came from
        mine            whether you organized it, or it's a personal
                        event (no organizer or attendees) in any
                        loaded calendar
        organizer       `name` and `email`, or null
        response        your response: `yes`, `maybe`, `no-reply`, or
                        null
        attendee_count  attendees who are people (rooms and resources
                        aren't counted)
        attendees       the first 20 of them, each with `name`, `email`,
                        and `response` (`yes`, `maybe`, `no-reply`, `no`,
                        or null)
    Attendance needs `email`; without it, `mine` is false and `response`
    null.

    Filters: `--with {name}` keeps only events whose organizer or an
    attendee who is a person matches {name}, checking every attendee, not
    only the 20 in `attendees`. Names and email addresses are split into
    words (runs of letters and digits), and every word of {name} must
    start one of the person's words, in any order, ignoring case: `zach`
    matches `Zachary Kim`, `"Loan Bui"` matches `bui.loan@example.com`,
    and `ann` doesn't match `Joanna`. A {name} without letters or digits
    is an error. `--search {text}` keeps only events whose title,
    location, or description contains {text}, ignoring case, as typed
    (`1:1` works). Both repeat, and an event must match every one: >
        meta-notes calendar --date 2026-09-28..2026-10-02 --with zach
        meta-notes calendar --with zach --search 1:1 --json
<   With a filter, only days with a matching event are listed, each with
    only those events; with none, the output is `No matching events.` (and
    an empty `days`). In `--json`, each event also has `matches`:
        with            one entry per `--with`: `name`, and `people`,
                        each organizer or attendee that matched (`name`,
                        `email`, `response`; null `response` for an
                        organizer who isn't an attendee)
        search          one entry per `--search`: `text`, and `fields`,
                        where it matched (`title`, `location`,
                        `description`)
    Descriptions are searched but never shown. Without a filter, events
    have no `matches`.

    Cache: each export is parsed once into `.meta-notes-cache/calendar/`,
    keyed by the export's name, size, and modification time and the loaded
    calendars, and reused while they're unchanged. The cached copy leaves
    out events that ended more than 30 days before it was built, so a
    {period} starting earlier is read from the export itself. When no
    export is left in `ics/`, the newest cached calendar is used, with a
    warning that its export is missing (and that earlier events may be
    missing for such a period). With no export and no cache, the command
    fails and names the `ics/` folder to export into.

    Pruning: every run keeps the 5 newest exports in `ics/` and deletes
    older ones, and keeps only cached calendars built from those exports
    with the current `calendars` setting (with no exports, only the newest
    one), plus the one it used. It deletes only `.ics` and `.zip` files
    directly in `ics/` and files in `calendar/`, and lists each deleted
    path in `pruned`, or on stderr without `--json`.

`meta-notes cache clear`                        *meta-notes-cli-cache-clear*
    Delete every file in `.meta-notes-cache/calendar/` and report how many.
    It never deletes exports in `ics/` or the cache README, and a missing
    `calendar/` isn't an error. `--json` returns `deleted` (the paths) and
    `count`. It doesn't need the virtualenv.

`meta-notes conventions`                        *meta-notes-cli-conventions*
    Print, as markdown, the note syntax and editing rules the shipped
    skills follow (|meta-notes-skills|): the task model, status
    characters, tags and aliases, the project model, how to edit task
    lines with |meta-notes-cli-task-update|, carrying a task forward,
    ceremony markers, and structural changes. The status characters and
    tag aliases are generated from the definitions queries and
    updates use, so the text matches the installed CLI. Works outside a
    notes root and reads no notes. With `--json`, the object has `version`
    and `text`, the markdown.

`meta-notes prime`                              *meta-notes-cli-prime*
    Print, as markdown, a guide to the notes root for an agent to read at
    the start of a session: the folders and naming, the plan notes (with
    today's daily, weekly, quarterly, and yearly paths), the working day, the time log, projects, areas, resources,
    the archive, the commands for finding things, the shipped skills, and
    the full |meta-notes-cli-conventions| output. Today's paths, the tag
    groups, and the skills are generated. Outside a notes root it still
    succeeds and starts with a line saying no root was found. With
    `--json`, the object has `version`, `root` (null outside a root), and
    `text`. The guide, conventions included, stays under 10,000
    characters.

    Point agents at it with this line in the notes root's `CLAUDE.md`: >
        Run `meta-notes prime` at the start of every session and follow it.
<   Put personal preferences (routines, habits, other working hours) in
    `CLAUDE.md` too; the guide says they override it.

`meta-notes ceremony status [--date {day}]`     *meta-notes-cli-ceremony*
    Report which ceremony markers (|meta-notes-ceremonies|) are checked
    for {day}, a single `YYYY-MM-DD` (default: today), and the Monday to
    Sunday week containing it. A range or other period is a usage error.
    Daily planning and daily shutdown are read from {day}'s daily note,
    weekly review and weekly planning from the week's weekly note, at the
    paths |meta-notes-cli-note| uses. A missing note or marker makes its
    ceremonies not done; it isn't an error. Writes nothing. In a `personal`
    root (|meta-notes-config|) there is no daily shutdown, so it isn't
    reported.

    The output is one line per ceremony: >
        daily-plan:     done
        daily-shutdown: done 2026-09-26
        weekly-review:  not done (no note)
        weekly-plan:    not done (no note)
<   A date after `done` is the marker's `✅` date. `(no note)` and
    `(no marker)` say what's missing. With `--json`, the object has
    `date`, `week_start`, and `ceremonies`, each with `name`
    (`daily-plan`, `daily-shutdown`, `weekly-review`, `weekly-plan`),
    `note`, `note_exists`, `marker_present`, `done`, and `completed` (the
    `✅` date or null).

`meta-notes planning [--date {period}]`         *meta-notes-cli-planning*
    The planning record for each day of {period} (any `--date` form,
    default today): whether the daily note exists, whether the day was
    planned (its `plan complete` marker is checked, or a Time Block row
    has a Plan other than `no plan`), and how many Time Block Plan cells
    are `no plan` or crossed out (in single tildes), then totals. A
    missing note counts zero. Writes nothing. Output: >
        2026-09-21: planned, 1 no plan, 2 crossed out
        2026-09-22: no note
        Total: 1 of 2 days with a note, 1 planned, 1 no plan, 2 crossed out
<   With `--json`: `start`, `end`, `days` (each with `date`, `note`,
    `note_exists`, `planned`, `no_plan`, `crossed_out`) and `totals`
    (`days`, `notes`, `planned`, `no_plan`, `crossed_out`).

`meta-notes checkin status|wait|actual`         *meta-notes-cli-checkin*
    Stay-on-task check-ins against the daily note's `### Time Block` table
    (rows such as `|  9:15am | plan | actual |`). `status [--date {day}]
    [--at {time}]` reports the current row (the last at or before {time},
    24-hour `HH:MM`, default now) with its Plan and Actual, and the
    unfilled rows: rows before it with an empty Actual, since the last
    filled one. `wait [--every {minutes}] [--end {time}]` sleeps until a
    check-in is due, `{minutes}` after it starts or at {time}, whichever is
    first, then prints the `status` and exits; `reason` is `due` or `end`
    (at once when it starts at or after {time}). Run it as a background
    command and the agent that started it wakes when it exits; no hooks are
    needed. `actual {time} {text} [--through {time}] [--force]` writes
    {text} into the Actual cell of the row at {time} (`HH:MM` or `9:15am`)
    or of every row through `--through`. A filled cell is skipped unless
    `--force`; `|` in {text} becomes `/`. An unknown row, a missing note,
    or empty text is an error and nothing is written. `status` and `wait`
    write nothing. With `--json`: `status` and `wait` return `date`, `time`,
    `note`, `note_exists`, `current` (`time`, `plan`, `actual`, or null) and
    `unfilled` (`time`, `plan`), and `wait` adds `reason`; `actual` returns
    `note`, `written` and `skipped`.

    Settings, in the `[checkin]` table of `.meta-notes`:
        interval        minutes between check-ins. Unset: 30.
        end             end of the workday, `HH:MM`. Unset: `17:30` in
                        a work root, `21:00` in a personal one.
    The `checkin` skill (|meta-notes-skills|) drives these commands.

`meta-notes time-block update {file} --time {time} ...`
                                                *meta-notes-cli-time-block*
    Write Plan and Actual cells of a note's `### Time Block` table, found
    by row time. Options: `--time {time}` (`HH:MM` or `9:30am`),
    `--through {time}` (every row through it, inclusive), `--plan {text}`,
    `--actual {text}` (at least one; both may be given), `--expect {text}`
    and `--create`. Text is padded to the column's width; `|` becomes `/`
    and newlines spaces. A cell that isn't empty is only overwritten when
    `--expect` equals its current text (compared stripped); with no
    `--expect` every target cell must be empty. `--expect` applies to every
    target cell, Plan and Actual. On a mismatch nothing is written and the
    error names each row, column and current text; with `--json`, `current`
    lists them as `time`, `column` and `text`, so the caller can re-read
    and retry. Also an error, with nothing written: no Time Block, a
    missing row without `--create`, a ragged table (a column whose cell
    widths differ between rows), and text wider than its column (the
    error gives the column's width and the text's length; nothing is
    truncated or widened). `--create` adds a missing `--time` row in time
    order, padded to the table's widths; it does nothing when the row
    exists, and can't be combined with `--through`. With `--json`: `file`,
    `written` and `created` (row labels). The `daily-plan` skill
    (|meta-notes-skills|) fills the Plan with it; `checkin actual` fills
    the Actual of today's note.

`meta-notes time-block replace {file} --time {time} --through {time} --expect {rows} --text {rows}`
    Rewrite the rows from `--time` through `--through` in one call, all or
    nothing. `--expect` is the rows as the caller read them and `--text`
    the new rows, each line `| time | plan | actual |` with one cell per
    header cell; padding is optional, the CLI pads to the file's widths
    and right-aligns the times. `--expect` is compared cell by cell,
    stripped; any difference writes nothing and lists each row, column
    and current text (`current` with `--json`). Every row of the range
    must be in `--text` (no deleting); new times inside the range are
    added in time order. Times outside the range, a duplicate time, a
    wrong cell count and text wider than its column are errors naming the
    row. `update` and `checkin` find Plan and Actual by the table's
    header names (any case, any order), not by position; a table without
    both headers is an error naming the headers it has. With `--json`:
    `file`, `written` and `created`.

`meta-notes time-log append {file} --text {line} ...`
                                                  *meta-notes-cli-time-log*
`meta-notes time-log update {file} --expect {text} --text {text}`
    Edit the entries under a note's `### Log`. An entry is a `- ` header
    line plus every indented line under it. Both commands check that the
    log still holds what the caller expects and otherwise write nothing,
    so they don't overwrite what you changed in Vim meanwhile. Times are
    `HH:MM` or `9:30am`.

    `append` adds one entry at the end. Options: `--text {line}` (the
    header, `- text #tags`), `--start {time}` (default: now), `--end
    {time}` (default: open), `--note {text}` (an extra `* note` line,
    repeatable), `--prev {line}` and `--prev-start {time}` (the last
    entry's header, exactly, and start), `--prev-open` (the last entry has
    no `end:`; without it, it must have one), `--close-prev` (write the
    last entry's `end:` as `--start`; needs `--prev-open`) and `--first`
    (the log is empty; replaces the `--prev` options). A mismatch writes
    nothing and shows the last entry (`current` in `--json`).

    `update` replaces a contiguous run of whole entries with zero or more.
    `--expect {text}` is the exact text of those entries, starting at a
    header and ending at an entry's last line; `--text {text}` replaces it
    (empty deletes), so edit, split, merge and delete all use it. No match
    is an error that shows the likely entries, `~` marking lines that
    differ (`current` in `--json`); two matches is an error too. Each new
    entry needs a header, a valid `start:` and an `end:` that is valid and
    not before its start; only the log's last entry may be open. Any
    failure writes nothing.

    A gap or overlap with a neighbouring entry is written anyway and
    reported as a warning (`*Gap of N min*`, `*Overlap of N min*`; in
    `--json`, `warnings`). With `--json`: `file` and `written` (an array
    with one item per new entry, each with `line` and `text`). The
    `daily-shutdown` skill (|meta-notes-skills|) uses them.

`meta-notes projects [--warnings]`              *meta-notes-cli-projects*
    List every project directly in `project/`: each note, and each folder,
    whose home note is its `Home.md`. Archived projects aren't listed. A
    project's fields are the `key: value` items of the first list after
    its home note's title; `status` is `active` when missing. Its tasks
    are the tasks in its note or folder plus tasks anywhere with its
    `tag`. Reads notes only; no git history or file times.

    Each line has the path, status, latest date, last review (or
    `never`), and warnings. The latest date is the latest `YYYY-MM-DD`, up
    to today, in the project's file names, heading lines, and tasks other
    than `#review` tasks. The last review is the latest completion date of
    a completed `#review` task. Warnings, with a 30-day threshold:

        no-home-note        a folder project without `Home.md`
        no-next             active, and no open task tagged `#next`
        no-recent-activity  active, and no latest date in the last 30 days
        review-overdue      not `done`, and no review in the last 30 days

    `--warnings` lists only projects with a warning. Warnings never make
    the command fail. With `--json`, the object has `projects`, each with
    `path`, `home` (or null), `status`, `tag` (or null), `last_review`,
    `latest_date` (dates or null), `open_tasks`, `completed_tasks`, and
    `warnings`.

`meta-notes project brief {path} [--since {day}]`
                                                *meta-notes-cli-project-brief*
    Report one project's full state: its fields, files, tasks, dates, and
    warnings. {path} is a note or folder directly in `project/` or
    `archive/project/`, relative to the notes root or absolute inside it;
    `.md` and a trailing `/` are optional. Anything else, such as an area
    or a note inside a folder project, is an error. Reads notes only.

    The home note, fields, tasks, latest date, last review, and warnings
    are the ones |meta-notes-cli-projects| reports for the project, so the
    two commands agree. The project's tasks are those in its note or
    folder plus tasks anywhere with its `tag`; canceled and rescheduled
    tasks are left out. Files include every file in the project, markdown
    or not, except names starting with `.`; their modification dates are
    shown but never used for the latest date.

    The text output starts with the path, status, tag, latest date, last
    review, and warnings, then these sections, leaving out empty ones:

        Files               size, modification date, and path
        Deadlines           open tasks tagged `#deadline`
        Scheduled reviews   open `#review` tasks with a due date
        Open                open tasks, except `#later` ones
        Later               open `#later` tasks
        Completed           completed tasks in the window

    Task lines are `{file}:{line}  {text}`, the target
    |meta-notes-cli-task-update| takes. Deadlines and scheduled reviews also appear under Open (or
    Later). A completed task's date is its `✅` date, or its due date
    without one; completed tasks dated on or after `--since {day}`
    (YYYY-MM-DD, default 90 days ago) are listed, and the heading gives
    how many are listed of the project's total.

    With `--json`, the object has `project`, with `path`, `home` (or null),
    `status`, `tag` (or null), `fields` (every field, keys lowercase),
    `latest_date` and `last_review` (dates or null), `has_next` (an open
    `#next` task exists), `warnings` (names, as for `projects`), `files`
    (each with `path`, `size`, and `modified`), `open`, `later`,
    `deadlines`, `scheduled_reviews`, `completed` (tasks as `tasks`
    returns them, without `section`), `completed_total`, and `since`.

`meta-notes --version`                          *meta-notes-cli-version*
    Print `meta-notes {version}`, where {version} is MAJOR.MINOR.PATCH.
    When the plugin directory is the top level of a git checkout, the
    commit follows, with `-dirty` if tracked files have uncommitted
    changes: >
        meta-notes 0.1.0 (f20d0de-dirty)
<   Works from any directory and ignores a subcommand given with it.
    |:MetaNotesVersion| shows the same line in Vim.

The CLI changes only the working tree. It never stages or commits.

Notes root ~
                                                *meta-notes-cli-root*
Paths in arguments and output are relative to the notes root, which is the
first of:
    1. `--root {dir}`
    2. the `META_NOTES_ROOT` environment variable
    3. the nearest directory, starting from the current one, that contains
       the `.meta-notes` sentinel created by |meta-notes-cli-init|

The upward search checks each directory only for `.meta-notes`. It stops
after `$HOME`, and stops quietly at the first directory you can't read,
write, and enter. If it finds nothing, the command fails and suggests running
`meta-notes init` or passing `--root`. An explicit `--root` or
`META_NOTES_ROOT` is used as given, with or without a sentinel.

The plugin always passes `--root` with Vim's current directory.

Config ~
                                                *meta-notes-config*
The `.meta-notes` sentinel is also the notes root's config, read as TOML.
The comment line `init` writes is valid, empty config, so every setting has
its default until you add one. Settings are grouped in tables named for the
command that uses them; unknown tables and keys are ignored. Commit the file
with your notes. `init` never changes it, even with `--force`;
`init --mode personal` writes the mode into a new one.

Only commands that use settings read it. When it isn't valid TOML, those
commands fail with an error naming `.meta-notes` and the line of the error;
other commands, and finding the notes root, are unaffected.

The root's mode is a top-level key, set before any table: >
    mode = "work"                   # "work" or "personal"; unset: "work"
<
Anything else is an error naming the two choices. `meta-notes prime` states
the mode, and its `--json` and that of `conventions` carry `mode`.

The mode sets the working day, from one place (scripts/meta_notes/hours.py)
that `prime`, `conventions` and `checkin wait` read: `work` is 08:00 to
17:00, Monday to Friday (the check-in ends at 17:30 unless `[checkin] end`
says otherwise); `personal` is 07:00 to 21:00, every day of the week, with
no work cutoff, and the check-in ends at 21:00. These aren't configurable.
In a personal root, `meta-notes note daily` uses
`resource/template/daily-personal.md` when it exists (Time Block 7:00am to
9:00pm, log line `start day:`); the shipped one is
`templates/daily-personal.md`, which `meta-notes init --mode personal`
installs. Re-running `init` never changes the mode.

The settings for |meta-notes-cli-calendar|: >
    # meta-notes notes root. Created by `meta-notes init`; keep and commit it.

    [calendar]
    email = "me@example.com"        # whose declines to hide; unset: none hidden, warning
    timezone = "America/New_York"   # display timezone; unset: system local
    stale_days = 3                  # unset: 3
    calendars = ["me@example.com"]  # zip members to load; unset: all
<
The settings for |meta-notes-cli-checkin|: >
    [checkin]
    interval = 30                   # minutes between check-ins; unset: 30
    end = "17:30"                   # end of the workday; unset: 17:30 work,
                                    # 21:00 personal
<
Output ~
                                                *meta-notes-cli-json*
Output is human-readable text by default, with errors and warnings on stderr.
With `--json`, every command writes exactly one JSON object to stdout and
nothing to stderr, whether it succeeds or fails: >
    {"ok": true, "moves": [...], "links_updated": [...], "warnings": []}
    {"ok": false, "error": "Source not found: project/foo.md", "warnings": []}
<
`move` and `rename` return `source`, `dest`, `moves` (`[old, new]` pairs),
and `links_updated` (files whose wiki-links were rewritten). `archive` adds
`items` with a result per archived path. `tasks` returns `tasks`, each with
`file`, `line`, `text`, `status`, `start`, `due`, `time`, `recurrence`,
`recurs_from_completion`, `completed`, `tags`
(canonical names without `#`), and `section` (the section it is listed in:
`overdue`, `due`, `scheduled`, `ready`, `future`, or `undated`), in report
order. A task under several tags with `--group-by tag` appears once.
`task add` returns `file`, `line` and `text` of the added line.
`task update` returns `file`, `line`, `old` and `new` (the line before and
after), `changed`, and `created` (null, or `file`, `line` and `text` of the
next occurrence a recurring completion inserted above the line); when the line didn't match `--expect`, it fails with
`file`, `line`, and `current`, the line's current text. `note` returns `path`, `exists` (whether the
note existed before), `created` (whether this command wrote it), and
`template` (the template used, or null); with `--render` and a new note, it
also returns `content`, the rendered note. `--version` returns `version`,
`commit` (the short hash, or null), and `dirty`. Output from template commands
appears only in `content` or the written note, never on stdout.
`calendar`, `cache clear`, `conventions`, `ceremony status`, `planning`, `checkin`, `time-block update`, `time-block replace`, `time-log append`, `time-log update`, and
`projects` return the fields listed under each command above.

The exit status is non-zero on failure. `--root` and `--json` may come
before or after the command name.

10. PLANNING SKILLS                             *meta-notes-skills*

The plugin ships Claude Code skills in `skills/`, linked into a notes root's
`.claude/skills/` by |meta-notes-cli-init|. Re-run `meta-notes init` after
updating the plugin to link new ones. Each planning skill states a time
budget, starts by running |meta-notes-cli-conventions|, reads notes through
focused CLI queries, edits task lines only with |meta-notes-cli-task-update|,
and can be stopped at any point.

    daily-shutdown  End of each workday (work roots only), about 15
                    minutes: collect loose items into tasks, PR check, a next step per project
                    worked on, the time-log check, a Follow up list,
                    commit (after you confirm), and `shutdown complete`.
                    Offers daily-plan.
    daily-plan      After shutdown or the next morning, 10-15 minutes:
                    plans today if it has no plan, otherwise the next
                    workday. Fills the Time Block Plan column.
    weekly-review   Friday morning: the Monday to Friday week, a summary
                    for your manager in the weekly note's `## Review`,
                    commitments, project warnings, and a `#later` scan.
                    Reminds you that weekly-plan is next.
    weekly-plan     Friday afternoon: capacity from next week's calendar
                    (|meta-notes-cli-calendar|, or a screenshot when
                    there's no export), deadlines, and 3-5 priorities in
                    next week's `## Plan`.
    task-cleanup    Anytime, 5-10 minutes: overdue and undated tasks,
                    oldest first, in batches.
    project-review  One project at a time.
    checkin         During the workday: runs |meta-notes-cli-checkin|
                    `wait` in the background, and when it wakes asks what
                    you've done and whether you're on plan, fills the Time
                    Block's Actual column, and helps when you switch
                    tasks. Offers daily-shutdown at the end.
    time-block      Anytime: plan, replan, fix or fill the Time Block and
                    Time Log through |meta-notes-cli-time-block| in your
                    style: lowercase, `mtg:` meetings untouched, past plans
                    that didn't happen wrapped in `~~ ~~` with a short
                    Actual, Actual blank when the plan happened.
    calendar        Anytime: answers questions about your meetings
                    (with someone, about a topic, a 1-1, free time)
                    with |meta-notes-cli-calendar| `--with` and
                    `--search`. Read-only, with no time budget, and it
                    doesn't run |meta-notes-cli-conventions|.

In a `personal` root (|meta-notes-config|) the skills read the mode from
|meta-notes-cli-conventions| and follow the personal day: no PR, Slack or
email steps; the next day is tomorrow, weekends included; `daily-shutdown`
doesn't apply and `daily-plan` runs on its own; `weekly-review` and
`weekly-plan` are on Sunday and cover Monday to Sunday, with no manager
summary; `calendar` free time is 7:00 to 21:00, with no 1-1s; and in
`time-block` `work:` is the exception instead of `pers:`.

Ceremony markers ~
                                                *meta-notes-ceremonies*
The daily and weekly templates carry checklist lines that record whether a
ceremony was done:

    daily note      `- [ ] plan complete`       daily planning
                    `- [ ] shutdown complete`   daily shutdown (work)
    weekly note     `- [ ] review complete`     weekly review
                    `- [ ] plan complete`       weekly planning

A skill checks its marker with `meta-notes task update --status x`, which
appends `✅ {today}`, the day the ceremony was done. A marker is done when
its status is `x` or `X`; its text is compared ignoring case and
surrounding whitespace, and may be anywhere in the note. The markers have no
dates, so task queries don't list them. The daily template also has a
`## Follow Up` section, and the weekly template `## Review` and `## Plan`.
Notes created before these were added have no markers; they read as not
done. |meta-notes-cli-ceremony| reports them.

11. AUTOSAVE AND AUTORELOAD                     *meta-notes-autosave*

Keeps Vim open on the notes root all day while agents edit the same notes
through the CLI: Vim saves your edits quickly, picks up other writers' edits
quickly, and never overwrites either. Everything is off by default and
applies only to buffers whose file is under a notes root (the nearest
directory with a `.meta-notes` file, found the way the CLI does; see
|meta-notes-cli-root|). Other buffers are never touched. Vim 8 or newer;
Neovim isn't supported.

Settings ~
                                                *g:meta_notes_autosave*
g:meta_notes_autosave           (default 0)
    Save notes buffers automatically.
                                                *g:meta_notes_autosave_delay*
g:meta_notes_autosave_delay     (default 1000)
    Debounce in ms. After `TextChanged` or `InsertLeave`, Vim waits this
    long without another change, then saves.
                                                *g:meta_notes_autoreload*
g:meta_notes_autoreload         (default 0)
    Set 'autoread' on notes buffers and check them for changes made
    outside Vim: on |FocusGained|, by the file watcher, and by the timer.
                                                *g:meta_notes_watch*
g:meta_notes_watch              (default 1)
    With autoreload on, run a file watcher job: `fswatch` (macOS) or
    `inotifywait` (Linux). One job per notes root, started with its first
    notes buffer and stopped when Vim exits. It watches the whole root
    except `.git/`, `.venv/` and `.meta-notes-cache/`, and checks a buffer
    when its file changes. If neither binary is found, a message says so
    once and the timer (below) is the only polling. Install fswatch with
    `brew install fswatch`; on Debian or Ubuntu, `sudo apt install
    inotify-tools` provides inotifywait. `meta-notes init` warns when the
    watcher is missing.
                                                *g:meta_notes_checktime_interval*
g:meta_notes_checktime_interval (default 0)
    With autoreload on, run |:checktime| on loaded notes buffers every this
    many ms. 0 turns the timer off. It runs alongside the watcher; use it
    alone, or as the fallback when the watcher isn't available.
                                                *g:meta_notes_disable_gitgutter*
g:meta_notes_disable_gitgutter  (default 1)
    When Vim starts with its working directory inside a notes root, run
    |:GitGutterDisable| (vim-gitgutter) once at VimEnter, so no signs
    show in the session, work files included. Started outside a notes
    root, GitGutter is left alone. It works whether or not autosave and
    autoreload are on, and does nothing when vim-gitgutter isn't
    installed. Set to 0 to leave GitGutter alone.
                                                *g:meta_notes_conflict_diff*
g:meta_notes_conflict_diff      (default 1)
    On a conflict, open a diff against the file on disk. With 0 only a
    message is shown.

Settings are read when used; after changing them in a running Vim, run
`:MetaNotesAutoreload on` to restart the watcher and timer.

Commands ~
                                                *:MetaNotesAutosave*
:MetaNotesAutosave [on|off|toggle]
    Turn autosave on or off, or toggle it (the default). Sets
    |g:meta_notes_autosave| and shows the state.
                                                *:MetaNotesAutoreload*
:MetaNotesAutoreload [on|off|toggle]
    The same for autoreload: |g:meta_notes_autoreload|. Also re-reads the
    watcher and timer settings and restarts them.
                                                *:MetaNotesAutoStatus*
:MetaNotesAutoStatus
    Show autosave (and its delay), autoreload, the watcher binary found and
    whether it's running, the timer interval and the conflict diff setting.

Recommended .vimrc ~

A fast machine: watcher plus a slow timer as a safety net >
    let g:meta_notes_autosave = 1
    let g:meta_notes_autoreload = 1
    let g:meta_notes_checktime_interval = 5000
<
A slow or busy machine: no polling and a longer debounce >
    let g:meta_notes_autosave = 1
    let g:meta_notes_autosave_delay = 3000
    let g:meta_notes_autoreload = 1
<
No watcher, timer only >
    let g:meta_notes_autoreload = 1
    let g:meta_notes_watch = 0
    let g:meta_notes_checktime_interval = 3000
<
Inside tmux, Vim only gets |FocusGained| if tmux passes focus events on.
Add to `~/.tmux.conf`: >
    set -g focus-events on
<
How it works ~

Autosave: after the debounce Vim runs |:checktime| on the buffer, then
`:update` only if the file on disk is unchanged since Vim read or wrote it.
It never forces a write and never triggers Vim's "changed since reading it"
prompt. It saves only the current buffer, in normal mode.

Autoreload: no check reloads a buffer while you are in insert mode; the
next one after you leave it does. When a buffer reloads, a message says
`meta-notes: reloaded <file> (changed on disk; u to undo)`, also for the
timer's and watcher's silent checks. A reload is
undoable: press `u`. That relies on 'undoreload' (Vim's default, 10000
lines); a longer note can't be undone, and the plugin doesn't change it.

Conflicts ~
                                                *meta-notes-conflict*
When a buffer has unsaved edits and its file changes on disk, the plugin
keeps your buffer, doesn't reload, pauses autosave for that buffer, and
says so. With |g:meta_notes_conflict_diff| on, a scratch split
`meta-notes://disk/<file>` opens beside it in diff mode, showing the file as
it is on disk. Merge what you need (|do|, |dp|) and write with |:w|; Vim
may ask whether to overwrite, which is your decision. A successful write
resumes autosave and closes the diff. Closing the split yourself just ends
diff mode. A file deleted on disk gives a warning; the buffer is kept.
